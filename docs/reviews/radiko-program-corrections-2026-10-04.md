# radiko番組表の不完全なデータと情報訂正への対応

## 取り込み方針

2026-10-04の実APIで確認した3種類のデータに対応する。局名や番組名で特例を分岐させず、データの状態で処理する。

| 状態 | 処理 | ログ・通知 |
| --- | --- | --- |
| 開始と終了が同じ | 同じ局の直後の開始時刻を終了として推定。後続がなければスキップ | 元時刻・推定時刻・対象IDをWarningに記録。異常通知なし |
| 番組名が空欄 | 有効な時刻範囲なら空欄のまま登録 | Warningに記録。異常通知なし |
| 終了が開始より前 | 当該番組をスキップ。他の番組を取り込む | 対象ID・元時刻をWarningに記録。異常通知なし |

不完全な項目の扱いは `Providers/Radiko/RadikoProgramScheduleNormalizer.cs` に分離した。後続の基準には別局や日時逆転した番組を使わず、XMLの並び順や同じ開始時刻の重複にも依存しない。

通信・XML全体の破損・局ID不一致・解析不能な日時は従来どおり取得失敗とする。通常の番組表更新開始・終了の通知は継続する。

## 次回取得時の訂正と予約

- 同じ局ID・開始日時の番組について、終了日時、番組名、説明、出演者、URLなどを最新取得内容へ更新する。
- 初回保存時の番組IDを維持する。終了日時を含む新しい生成IDに付け替えず、予約・録音履歴・UIからの既存参照を保つ。API取得結果の入力オブジェクトのIDは変更しない。
- Pending状態のradiko番組予約・キーワード予約は時刻と表示情報を更新する。タイムフリーの準備時刻も終了日時に追随させる。予約のID、関連するキーワードルール、保存先、余白、有効設定、実行状態は維持する。
- 状態を条件としたDB更新により、キュー投入済み・実行中・完了済み・失敗済みのジョブを変更しない。
- 番組と予約の更新を同じSQLiteトランザクションで行う。保存失敗時は両方をロールバックし、失敗した変更を次回の保存へ持ち越さない。スケジューラの起床通知はコミット後に行う。
- スキップや取得範囲外の番組を理由に既存番組を削除しない。通常の保存期限による削除は従来どおり。DBスキーマ・migration・既存の番組ID形式は変更しない。

同一番組とみなす範囲は同じ局・同じ開始日時。開始日時自体が移動する編成変更は別の放送枠として扱い、タイトル等の類似だけで予約を別番組へ移さない。今回、一般的な番組移動・取り消しの自動推定や過去の重複データの一括削除は行わない。

## 検証

- `dotnet test RadiCorder.slnx -c Release --no-restore`: ロジック475件、Web22件成功。スキップなし。
- 実APIから抜粋した最小fixtureでABC・CRT・RKKの処理とWarning記録を検証。日時解析・局判定等の異常を正常な空番組表にしない既存テストも継続。
- 予約追随、他サービス・別局への更新防止、再取得での重複防止、保存失敗のロールバック、実行状態の保護、保存済み録音の参照と時刻保持を検証。
- 保存済みの実API応答全文を本体APIとリポジトリへ渡し、ABC 485件・CRT 498件・RKK 687件の保存に成功。RKKは問題の1件だけスキップ。
- 実応答のABCを検証用に確定時刻・タイトルへ変更した次回応答を作り、推定データの差し替え、再取得、DBを閉じて開き直した後の保持、`PRAGMA integrity_check = ok` を確認。
- 全体テストで既存の曜日フラグ変換の誤りによる日曜日の失敗も見つかったため、予約テストの曜日変換を訂正し、予約余白の確認を固定した日曜日・火曜日のケースで実行するようにした。製品の曜日処理は変更していない。

公開番組表の取得以外の実サービス認証・再生・録音は実行していない。ユーザーの実DBには触れていない。

## Canaryへの追随

Canaryの番組名検証と前回DBからの増分期待値も新しい方針へ合わせる必要がある。独立した期待値の計算で同じ局・開始時刻の既存IDを保持し、終了時刻の更新漏れを故意に発生させた場合にも不一致を検出する。
